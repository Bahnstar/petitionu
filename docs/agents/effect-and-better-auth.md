# Effect 4 and Better Auth gotchas

Verified against `effect@4.0.6` and `better-auth@1.7.14` while building the server. Sources of truth: `apps/server/node_modules/effect/src/**`, the v4 examples inside the package (`apps/server/node_modules/effect/ai-docs/`) and `node_modules/better-auth/dist/**`. Read the source before trusting a v3-era example.

## Effect v3 to v4 renames

- `@effect/platform`, `@effect/rpc`, `@effect/sql` and `@effect/experimental` are now `effect/http`, `effect/rpc`, `effect/sql` and `effect/persistence`. Drivers stay separate: `@effect/sql-pg` (its own wire protocol, no `pg`) and `@effect/platform-node`.
- Services: `class X extends Context.Service<X, Shape>()("id") {}`, built with `X.of({...})` and `Layer.effect(X, effect)` (which also handles Scope; `Layer.scoped` is gone). Flags with a default: `Context.Reference`. `Layer.succeed(Tag)(impl)` is curried.
- `Effect.catchAll` is `Effect.catch`; `Effect.fork` is `Effect.forkChild`, `forkDaemon` is `forkDetach`; `Either` is `Result` (`Effect.result`); `Effect.async` is `Effect.callback`; `zipRight` is gone (`andThen`).
- Schema: `Schema.Union([...])` and `Schema.Literals([...])` take arrays; filters use `.check(...)`. `SqlSchema.findOne` fails with `NoSuchElementError`; `findOneOption` returns an Option.
- `HttpRouter` is a service plus layers (`add`, `serve`, `toWebHandler`). Mount fetch handlers with `HttpEffect.fromWebHandler`.

## HTTP and RPC

- `router.prefixed(...)` strips the prefix from `req.url`. Better Auth needs the full path, so it's mounted with `router.add("*", "/api/auth/*", ...)`.
- `RpcServer.layerHttp` defaults to WebSocket; the app passes `protocol: "http"` for `POST /rpc`.
- RPC middleware `headers` merge the HTTP headers with headers the client puts in the JSON body, and the body wins. CSRF, Origin and content-type checks therefore run in an `HttpRouter.middleware` on the real request (`src/Csrf.ts`), never in RPC middleware.
- `RpcClient.withHeaders` and the per-call `headers` option set message headers, not HTTP headers. Real HTTP headers (X-CSRF-Token) go through the client's fetch, as `makeApiClient` does.
- The raw `RpcClient` validates payloads before sending: a payload its schema rejects is a defect, not a typed error. The shared client (`makeApiClient` in `packages/domain/src/Client.ts`) encodes each payload against its schema first and answers a rejection itself, as `invalid` entries per field worded by the schema, without sending the call. A caller that skips the shared client and sends a payload the server's schema rejects gets a defect from the server's decode, before any handler runs. Payload schemas are strict (see AGENTS.md).
- A `defect` schema on `Rpc.make` doesn't keep internals out of responses: `RpcServer` encodes a handler's defect, an unreadable request and an unknown message with a fixed `Schema.Defect()`, cause chain included. `RedactedJsonSerialization` (`src/RpcDefects.ts`) replaces every defect in the outgoing messages, and the client reports it as an `unknown` error. `ActorMiddlewareLive` logs a procedure's defect with its stack and the procedure's name; the serialization logs the rest. Responses that can't be encoded log at Error; what's wrong with a request (malformed JSON, unknown tags, rejected payloads) logs as a warning cut to 500 characters, because any caller can send it. `RpcServer` throws a `TypeError` on some junk bodies, which looks like a server fault, so the serialization's `decode` rejects those shapes first.
- `MaxBodySize` only bounds a Node request's `arrayBuffer`: a Web request's reads and the stream `fromWebHandler` passes to Better Auth ignore it. `limitBody` (`src/BodyLimit.ts`) reads the body itself and hands on a `fromWeb` request holding it, which also makes the in-process test app behave like the Node server here, except that a Web request with no body at all (`body: null`) dies; send an empty string. Stopping early doesn't end the request on Node, so the 413 sets `Connection: close`. The shared client turns the 413 into an `invalid` entry: the RPC protocol reads any response as RPC messages, so without `filterStatus` the status is lost.
- Encoding starts from a schema's type side, so the type side must accept every value a form sends, and a check that should see what the user typed (e.g. a trimmed length) sits on the encoded side, before any decoding transformation; see `packages/domain/src/Inputs.ts`. A missing key's `messageMissingKey` is read from the encoded side when encoding and from the outer schema when decoding, so `Note` annotates both.
- `Schema.optional` is `optionalKey(UndefinedOr(...))`, and the JSON codec carries `undefined` as `null`. A key set to `undefined` is sent, as `null`: a field that accepts `null` (a petition's `deadline`, which it clears) takes that `null`, and one that doesn't decodes it as `undefined`, an omitted field. To leave such a field alone, leave out the key.
- With `errors: "all"`, every check on a schema runs, so two filters that can both fail report two messages for one field. For one message use one filter that returns it (a petition's `Goal`). A value of the wrong type fails the `optional`'s union, not its member, so a message for it annotates the `optional`.

## SQL and the job queue

- One statement per `sql.unsafe` call (extended protocol only). `PgClient` connects lazily: a bad URL surfaces on the first query.
- The Pg driver reads `timestamp` columns as `Date`s, truncated to milliseconds. Response DTOs carry them as `Timestamp` or `Deadline` (`packages/domain/src/Timestamps.ts`), which encode the ISO strings, so queries select the columns as they are and decode rows against the DTO's type side (`Result: Schema.toType(PetitionDto)`).
- A `PersistedQueue` offer made inside `sql.withTransaction` joins that transaction, so queueing a job commits or rolls back with the write. Delivery is at least once: handlers must be idempotent. To cancel a job, complete it and log why; there's no cancel API.
- The SQL queue store uses the database clock, so `TestClock` can't advance it. Tests drive the queue through `test/support/jobs.ts` (`drain`, `elapse`). The verification job's 60-second deferral writes to the store's table directly and `verificationJobs` reads it, which an Effect upgrade could break.
- A queue id is never reusable: `offer` silently ignores an id the table already holds, including a failed or completed job's, until `layerCleanup` removes it (the app doesn't run it). The `id` column is `VARCHAR(36)`. To run a job again, offer it without an id, and act on the job in hand by the `id` that `take` passes, not by anything in its payload.

## Tests

- `it.effect` runs on a fake clock that drives neither Postgres `now()` nor Better Auth's `Date.now()`; use `it.live` for anything touching them.
- `layer(...)` from `@effect/vitest` shares one built layer across a file; pass `excludeTestServices: true` when building it needs real sleeps (see the policy matrix).

## Better Auth

- Field and table names are mapped onto the existing schema in `src/Auth.ts` (`users`, `account`, `session`, `verification`, `rate_limit`). Existing users got a `credential` account holding their legacy bcrypt hash, so old passwords keep working.
- Hashing uses `bcryptjs` at cost 12: native addons can't load from the bundled image.
- Emailed links point at SPA pages (`/auth/confirm`, `/auth/magic`, `/reset`) built from the token, not Better Auth's URLs, because its verify URLs act on GET and mail scanners would consume them. The page calls the API when the user clicks.
- `/verify-email` and `/magic-link/verify` are GET and sign in, and Better Auth's origin check skips GET, so a before-hook requires the app's own header (`x-petitionu-app`, `appRequestHeaders` in the domain package). A navigation, image or plain link can't set one, and another site's `fetch` with it needs a CORS preflight nothing here grants: `OPTIONS` gets no `Access-Control-Allow-*`. That holds in browsers that send no fetch metadata, such as older Safari; `Sec-Fetch-Site` only adds a refusal when it's present and isn't `same-origin`. Tests get the header from `Browser.authGet`. `POST /reset-password` also signs in, but takes JSON only, which no other site can send without a CORS preflight.
- `POST /link-details` (`src/EmailLinks.ts`, behind the same header, 20 a minute) tells the Confirm and magic-link pages which address a token is for, and which other account this browser would leave. It reads a Confirm token as a JWT and finds a magic link's row by its hash, so it uses neither; only `/magic-link/verify` consumes the row. Every link that can't be used gets the same `INVALID_LINK`. An old Confirm link on a confirmed address signs nobody in, so it reports no account switch.
- Password reset doesn't set `emailVerified`; the reset hook does. Confirmation (`UserConfirmed`) runs once per user, inside the transaction that sets `confirmed_at`.
- A magic-link sign-in by an unverified user deletes that user's password account and sessions (Better Auth's anti-takeover rule). The user then needs a password reset.
- `requireEmailVerification` is on, so an unconfirmed account can't sign in with a password. The refusal (`EMAIL_NOT_VERIFIED`) comes after bcrypt, from the user row read before it, and sends a new confirmation link. Sign-up creates no session. `autoSignInAfterVerification` is on, so Confirm signs in whoever clicks.
- A sign-in reads the user, then the account in a separate query (`advanced.database.joins` is off). So every confirmation must remove or replace the password before `email_verified` flips: Better Auth does this for magic links and resets, and `revokeUnprovenAccess` for Confirm. `test/confirm-race.test.ts` pins that order with Postgres triggers.
- Sign-up doesn't prove an address, so only proving the password keeps it. `POST /verify-email/password` (`src/EmailLinks.ts`, 5 a minute, same bcrypt verify as sign-in) confirms and keeps it; `/verify-email` is a GET and can't carry one. A wrong password is 400 `INVALID_PASSWORD` and leaves the token usable. A confirmed account gets the same answer whatever was sent, so an old link can't test passwords. `/verify-email` itself is refused with 409 `CONFIRM_REMOVES_PASSWORD` while the account has a password, and changes nothing; with `removePassword=true` it deletes the password account and sessions, and the response carries `passwordRemoved: true`.
- Both ways confirm through `revokeUnprovenAccountAccess`: its lock stops a concurrent click ending the session the first click created. Keeping the password shows it an account with nothing linked (`findAccounts` returns none). A click that loses the lock stops waiting after 2 s and can get an unverified user back, or an error if the lock goes as it looks, so the password path retries (`settleConfirmation`). `/verify-email` can't, and goes on to flip `email_verified` itself.
- A failed CSRF reload makes `afterAuthChange` load its `destination` in full, which loses any state on the page. Sign-up starts no session, so the register page doesn't call it and its check-your-email screen can't be lost. The confirm page sends a click that removed a password to `/auth/confirm?password_removed=1`, which shows the notice without a token.
- `__Host-` cookies need `Secure`, `Path=/` and no `Domain`, or browsers drop them. Chromium stores `Secure` cookies over plain HTTP only on localhost and `127.0.0.1`.
- With `requireEmailVerification` on, sign-up answers a registered address as it answers a new one, with a synthetic user. Set nothing that depends on the user existing. The owner gets `accountExistsEmail` from `onExistingUserSignUp`.
- Rate limits are per client address from `CLIENT_IP_HEADER`; without a resolvable address all clients share one bucket.
- Better Auth disables its origin check when `NODE_ENV=test`; the app sets `disableOriginCheck: false` so tests see production behaviour. Tests send `Origin` like a browser (`makeBrowser`).
- The session cookie is `better-auth.session_token` (with a `__Secure-` prefix on https). `getSession` doesn't refresh it; the web app calls `get-session` on load.
